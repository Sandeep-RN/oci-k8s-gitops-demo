# Node drain on OKE: the PDB keeps the app up (2026-10-24)

Evidence for #18. This ran on the **short-lived OKE target** (ADR 0015), which
is torn down by 2026-11-15. The long-lived k3s node is a single node and cannot
show this (ADR 0001).

## Setup

- OKE Basic cluster, 2 × `VM.Standard.E5.Flex` workers, Kubernetes v1.36.4.
- `node-a` in FAULT-DOMAIN-1, `node-b` in FAULT-DOMAIN-2 (same availability
  domain; ap-hyderabad-1 has only one).
- Backend: 2 replicas, topology spread on `kubernetes.io/hostname` with
  `whenUnsatisfiable: DoNotSchedule`, PDB `minAvailable: 1`.
- `postgres-0` runs on `node-b`. The drain targets `node-a` so the test isolates
  the backend PDB instead of also restarting the database (that case is covered
  by the fail-fast test in #26).
- Traffic: a loop on a laptop sends `GET /<code>` (a real redirect, which reads
  from Postgres) to the public load balancer every 0.2 s, with a 5 s timeout.

Node names are replaced with `node-a`/`node-b`; addresses are left out.

## 1. Before

```text
NAME     STATUS   FAULT-DOMAIN
node-b   Ready    FAULT-DOMAIN-2
node-a   Ready    FAULT-DOMAIN-1

NAME      MIN AVAILABLE   ALLOWED DISRUPTIONS
backend   1               1

backend-569d7cdb98-dwkzj   1/1   Running   node-a
backend-569d7cdb98-zs2p6   1/1   Running   node-b
postgres-0                 1/1   Running   node-b
```

## 2. Drain `node-a`

```text
$ kubectl drain node-a --ignore-daemonsets --delete-emptydir-data --timeout=180s
node/node-a cordoned
evicting pod link-shortener/backend-569d7cdb98-dwkzj
evicting pod argocd/argocd-server-...            (plus other ArgoCD pods and one CoreDNS replica)
pod/backend-569d7cdb98-dwkzj evicted
node/node-a drained                               (47 s in total)
```

The PDB allowed the eviction because one backend pod stayed available. After
the drain it allows no more:

```text
NAME      MIN AVAILABLE   ALLOWED DISRUPTIONS
backend   1               0

backend-569d7cdb98-zs2p6   1/1   Running   node-b
backend-569d7cdb98-zsq8w   0/1   Pending   <none>
```

The replacement pod stays **Pending** on purpose. `node-a` is cordoned, and the
strict spread forbids a second backend pod on `node-b`:

```text
FailedScheduling  0/2 nodes are available: 1 node(s) didn't match pod topology
spread constraints, 1 node(s) were unschedulable.
```

This is the chosen trade-off: during maintenance the app runs on one pod rather
than stacking both pods in one fault domain.

## 3. Try to evict the last backend pod

Draining `node-b` for backend pods only (`--pod-selector`), so Postgres is not
touched:

```text
$ kubectl drain node-b --pod-selector=app.kubernetes.io/name=backend --timeout=30s
node/node-b cordoned
evicting pod link-shortener/backend-569d7cdb98-zs2p6
error when evicting pods/"backend-569d7cdb98-zs2p6" -n "link-shortener" (will retry after 5s):
  Cannot evict pod as it would violate the pod's disruption budget.
error: unable to drain node "node-b" ... global timeout reached: 30s
```

The PDB blocked the eviction (the API answers 429 Too Many Requests, which
`kubectl drain` retries until its timeout). The last pod kept running.

## 4. Restore

```text
$ kubectl uncordon node-a node-b
deployment "backend" successfully rolled out

NAME      MIN AVAILABLE   ALLOWED DISRUPTIONS
backend   1               1

backend-569d7cdb98-zs2p6   1/1   Running   node-b
backend-569d7cdb98-zsq8w   1/1   Running   node-a
```

The pending pod scheduled on `node-a`, so there is again one pod per fault
domain. All four ArgoCD applications were Synced/Healthy afterwards. No
manifest changed: drain and uncordon are cluster operations, not
`kubectl apply`.

## Traffic during the whole run

The loop ran from 15 s before the drain until the restored rollout finished
(23:26:05 to 23:31:04 IST), covering steps 2 to 4.

| Measure | Value |
|---|---|
| Requests | 370 |
| Non-302 responses or connection errors | **0** |
| Slowest request | 0.36 s |
| Longest gap between responses | 2.33 s (see note) |

Note on the gap: the longest gaps (1.2-2.3 s) are all between 23:28:20 and
23:28:27, a quiet minute between steps 2 and 3, and every request in that
window still took 0.18-0.26 s. They come from the client loop on the laptop
(process start-up on Windows), not from the service.

## What this shows, and what it doesn't

- Shows: a voluntary disruption (drain) of one node does not interrupt the
  service, and the PDB refuses a disruption that would take the last pod.
- Doesn't show: an *involuntary* node failure (a crash is not an eviction, so a
  PDB cannot prevent it), or a drain of the node that runs Postgres, which is a
  single replica and would be a short outage that the app answers with 503s
  (#26).
- Related finding: a rollout earlier left both backend pods on one node despite
  the strict spread, because spread is checked only when a pod is scheduled.
  The pods were rebalanced by hand before this test (#42).
