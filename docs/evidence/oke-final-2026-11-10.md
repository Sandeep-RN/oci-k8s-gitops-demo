## Setup

- OKE Basic cluster, 2 × `VM.Standard.E5.Flex` workers, Kubernetes v1.36.4.
- `node-a` in FAULT-DOMAIN-1, `node-b` in FAULT-DOMAIN-2 (ap-hyderabad-1 has
  one availability domain).
- Backend: 2 replicas, topology spread with `DoNotSchedule`, PDB
  `minAvailable: 1`. Traefik: one pod per node, PDB `maxUnavailable: 1`.
- `postgres-0` runs on `node-b`. The drain targets `node-a`, so the test
  isolates the stateless tiers and does not restart the database.
- Traffic: a loop on a laptop sends `GET /<code>` (a real redirect that reads
  from Postgres) to the public URL with a 0.5 s pause between requests (in practice about
  0.6 to 0.8 requests a second), a 5 s timeout, and one log line per request. Server-side numbers come from Prometheus, read as running totals
  before and after each test (`increase()` cannot see the first increment of a
  new series; Traefik's service label is `exported_service`).

Node names are replaced with `node-a`/`node-b`; addresses are left out.

## 1. Drain and PDB (2026-11-08, 00:02 to 00:29 IST)

1. Drain `node-a` (`--ignore-daemonsets --delete-emptydir-data`). The backend
   and Traefik pods on it were evicted; their replacements stayed **Pending on
   purpose** (the node is cordoned and the strict spread forbids a second pod
   on `node-b`). Prometheus, Grafana and Alertmanager moved to `node-b` within
   about a minute.
2. Try to drain `node-b` for backend pods only (`--pod-selector`). The PDB
   refused: six retries over the 30 s timeout, the last backend pod stayed up.
3. Restore: `kubectl uncordon` on both nodes, the pending pods scheduled, one
   backend and one Traefik pod per node again, PDBs back to allowing one
   disruption, all 10 Argo CD applications Synced and Healthy.

| Measure | Value |
|---|---|

| Non-302 responses or connection errors | **0** |
| Slowest request | 0.57 s |
| Longest gap between responses | 2 s |
| Backend 5xx in Prometheus | none |
| Traefik 5xx total (before and after) | 1 and 1 (the earlier 502, see section 4) |

Compared with 2026-10-24 (370 requests, 0 failures, Traefik not part of the

the public URL kept answering through the other one.

## 2. Rollout under traffic (2026-11-08, 02:15 to 02:22 IST)

Trigger: a small landing-page change (app PR #23). Merging it ran the pipeline
that every change takes: build, Trivy scan, push, an auto-merged tag-bump PR in
the gitops repo, then Argo CD rolled the Deployment.

| Step | Time (IST) |
|---|---|
| PR merged | 02:15 |
| App CI finished (test, build, scan, push) | about 02:19:40 |
| Bump PR merged | 02:20 |
| New backend pods running, old ones terminated | about 02:22 |

Merge to live: about **7 minutes**. During the roll each new pod was 1/1 Ready
before its old pod started terminating.

| Measure | Value |
|---|---|
| Requests (02:13:59 to 02:28:35) | 514 |
| Non-302 responses or connection errors | **0** |

Note on the gaps: the gaps of 4 to 12 s are at 02:15, when the PR was merged
from the same laptop, seven minutes before the pods rolled. No request in the
log failed or timed out. They come from the client, not from the service.

## 3. The scan gate caught a real finding

The first CI run of that PR failed at the Trivy step: two HIGH CVEs in
`zlib1g`, both with a fix already in Debian, in the floating `python:3.12-slim`
base. The gate blocks only vulnerabilities that have a fix, so this was a real
blocker. Fix: upgrade that one package in the Dockerfile (with a comment to
remove it once the upstream image has the fix). The re-run passed, and nothing
vulnerable reached the registry.

## 4. The earlier 502

One 502 appeared in Traefik's counters on 2026-11-02 during a pod roll. The
backend recorded no 5xx, so Traefik produced it, probably a terminating pod
still in its endpoints for a moment. It did **not** recur in either test above.
That is a weak result: about one request every 1 to 2 s against a termination
window of a few seconds, one run each. A `preStop` sleep on the backend would
remove the race; it is not applied yet.

## 5. Alert proof (earlier, not re-run)

The fast burn-rate alert was proven on 2026-10-25 (#53): Discord shows
`RedirectErrorBudgetBurnFast` firing at 1:14 PM and resolved at 1:19 PM. A live
re-run was skipped on purpose; it needs a 5-minute outage of the public URL.

## What this shows, and what it doesn't

- Shows: a voluntary disruption (drain, rollout) of one node or one pod does not
  interrupt the service, the PDB refuses a disruption that would take the last
  backend pod, the pipeline takes a change to production in about 7 minutes, and
  the scan gate blocks a vulnerable image before it is pushed.
- Doesn't show: an *involuntary* node failure (a crash is not an eviction, so a
  PDB cannot prevent it), a drain of the node that runs Postgres (a single
  replica: a short outage, covered by the fail-fast behaviour in #26), or
  behaviour under heavy load: the loop sends less than one request a second.
- Screenshots of the dashboards, Argo CD, the certificate and the pipeline were
  captured on 2026-11-07 and are kept privately; they show private node
  addresses, so they are not committed.
